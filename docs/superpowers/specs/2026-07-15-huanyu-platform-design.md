# HuanYu（寰域）首版产品与系统设计

- 状态：五个设计章节均已确认
- 日期：2026-07-15
- 首版形态：桌面端 Web 全栈邀请内测
- 冷启动领域：软件开发与技术学习

## 1. 摘要

HuanYu 是一个以概念关系而不是熟人关系为中心的沟通平台。用户用一组带权重的寰点描述自己的爱好、特长、职业和专业；用户围绕多个寰点创建域并发布内容；内容和结构化评价持续改变用户、域、寰与寰点之间的权重。

平台的三个核心概念是：

- **寰点**：可被用户、内容、域和寰引用的概念节点，例如 Go、程序员、分布式系统、成都或某个粉丝群体爱称。
- **域**：用户创建的、由多个动态寰点共同定义的局部交流空间，是范围性的小寰。
- **寰**：唯一、官方、全局的总域，包含所有寰点、所有域和全部公开内容。

首版只验证一个核心闭环：

```text
用户建立寰点名片
  → 因寰点发现内容、域和其他用户
  → 在寰或域中发布 Markdown 内容
  → 系统提取并由发布者确认内容寰点
  → 其他用户针对具体寰点进行结构化评价
  → 生成可审计的三值证据
  → 更新三类权重投影
  → 名片、域向量和寰的全局热度发生可解释变化
```

## 2. 目标与首版边界

### 2.1 产品目标

首版需要证明：一小批开发者能够通过编程语言、框架、工具、岗位和技术方向等寰点找到相关内容与同类用户，进入相关域交流，并通过持续参与形成可解释的个人寰点名片。

### 2.2 交付目标

首版不是交互原型，而是可邀请真实用户使用的全栈内测版，具有真实账号、持久化数据、内容发布、寰点提取、搜索、评价、权重计算和系统配置。

### 2.3 技术约束

- 客户端：React + Next.js + TypeScript。
- 客户端只支持桌面端，不承担移动端响应式适配要求。
- 服务端：Go + Gin。
- 主数据库：PostgreSQL。
- 向量存储与召回：PostgreSQL + pgvector。
- 缓存、限流和任务唤醒：Redis。
- 图片：S3 兼容对象存储；本地和内测环境可使用 MinIO。
- 密码重置邮件：可替换 SMTP 适配器。
- 首版不依赖大模型直接生成寰点。

### 2.4 开发约束

- 代码和简介允许适量缩写，但不能牺牲可理解性。
- 关键业务规则、权重算法、异常边界和非显然逻辑必须有解释性注释。
- 模块职责和依赖方向必须清晰。
- 以最终功能点能否完整运行和验收作为主要判断标准。
- 不为未来可能出现的规模提前拆微服务。

## 3. 核心产品模型

### 3.1 寰

寰是唯一、官方、世界级的总域：

- 包含所有寰点。
- 包含所有用户创建的域。
- 包含全部公开内容。
- 维护寰与每个寰点的全局热度权重。
- 提供全局内容流、搜索、发现和聚合。

寰—寰点权重表示一个寰点在全平台范围内被真实用户绑定、关联和参与的热度，不表示该寰点比其他寰点更正确。

### 3.2 域

域是用户创建的、范围性的小寰：

- 创建时填写名称、描述和 2 至 10 个种子寰点。
- 所有域在首版均为公开域。
- 所有用户都可以发现和阅读域内容。
- 用户加入域后才能发布、回复和评价域内内容。
- 域与每个寰点之间具有动态主题权重。
- 种子寰点只提供初始方向，不永久锁定域的主题。
- 域内内容和有效互动会持续改变域—寰点权重。

域创建者在创建成功后自动成为普通域成员，并保留创建关联，但不获得额外管理权。首版不实现域治理、域管理员、成员选举或投票。域名称或描述确需纠错时只能由平台管理员处理。

### 3.3 内容归属

每条内容最多有一个直接发布语境：

- 未选择域时直接发布到寰。
- 选择域时直接归属于该域。
- 域属于寰，因此域内公开内容天然属于寰的公开内容集合。
- 域内内容在寰的内容流和搜索结果中标注所属域。
- 首版不允许一条内容同时直接归属于多个域。

内容采用统一模型：标题、Markdown 正文、内容类型、所属语境和多个已确认寰点。内容类型包括讨论、提问、经验分享和作品展示；首版只影响展示和筛选，不建立不同的数据结构。

## 4. 寰点模型

### 4.1 基本规则

- 所有寰点创建后立即进入寰。
- 寰点没有“等待进入寰”的候选状态。
- 新寰点可以权重很低，但仍属于寰。
- 官方治理的是寰点身份归一和展示秩序，不决定一个寰点是否有资格存在。
- 用户绑定寰点时，用户—寰点权重从 0 开始；声明关系不等于证明参与或能力。

### 4.2 产生方式

寰点通过 `origin_type` 记录怎样进入寰：

| 值 | 含义 |
|---|---|
| `USER_DEFINED` | 用户主动创建 |
| `CONTENT_DERIVED` | 从内容中提取并经发布者确认后创建 |
| `SYSTEM_PRESET` | 随系统初始化预设 |
| `SYSTEM_IMPORTED` | 系统管理员后续录入或批量导入 |

产生方式在创建后保持不变。

### 4.3 权威属性

寰点通过独立的 `authority_type` 记录当前依据：

| 值 | 含义 |
|---|---|
| `COMMUNITY` | 社区产生，没有额外权威背书 |
| `PLATFORM` | 由寰官方整理或确认 |
| `PUBLIC_STANDARD` | 来自公共标准或广泛共识的知识体系 |
| `EXTERNAL_AUTHORITY` | 来自可明确追溯的外部权威机构 |

权威属性历史保存在 `point_authority_records`，至少记录来源机构、来源名称、来源链接或外部标识、有效时间、确认人、确认时间、当前状态和变更原因。

系统预设不自动等于客观认证。权威属性也不证明某个用户具备相应能力。

### 4.4 系统预设与录入

首版初始化一组开发者冷启动寰点，包括：

- 编程语言：Go、Java、JavaScript、Python。
- 开发框架：Gin、Spring Boot、React、Next.js。
- 数据库：PostgreSQL、MySQL、Redis。
- 技术方向：分布式系统、微服务、前端开发、后端开发。
- 工具和平台：Git、Docker、Kubernetes。

预设数据使用稳定标识和版本号，初始化必须幂等。

平台管理员可以通过系统页面单条录入或批量导入寰点，设置规范名称、描述、别名、权威属性和客观依据，并触发向量生成。管理员录入和导入的产生方式固定为 `SYSTEM_IMPORTED`；初始化数据固定为 `SYSTEM_PRESET`。产生方式由真实创建路径决定，创建后不能由管理员改写。

用户从名片或普通创建入口新建时使用 `USER_DEFINED`；发布者从内容提取结果中创建新概念时使用 `CONTENT_DERIVED`。

### 4.5 同义归一

- 创建前按规范名称、别名、模糊相似度和向量相似度提示已有寰点。
- 用户仍可创建新寰点。
- 用户可以提交同义合并建议。
- 最终合并由平台管理员确认。
- 合并后保留一个规范寰点；旧名称成为可搜索别名。
- 用户绑定、内容关联、域关系和权重证据迁移到规范寰点。
- 相关但不完全同义的概念不合并。

## 5. 权重模型

### 5.1 三组关系

首版只计算：

1. 用户—寰点：个人参与与可信契合。
2. 域—寰点：寰点在局部域中的主题核心程度。
3. 寰—寰点：寰点在全平台中的参与热度。

### 5.2 用户—寰点双权重

内部独立保存：

- **参与权重**：发布、回复和其他有效参与形成的证据。
- **认可权重**：其他用户针对具体寰点给出的结构化认可或不认可。

对外显示一个综合契合数值、等级和颜色；用户可以展开查看参与值、认可值、证据摘要、最后计算时间和策略版本。

### 5.3 三值证据

每个有效业务动作产生：

- `+1`：正向证据。
- `-1`：负向证据。
- `0`：没有产生新证据，权重保持不变。

`0` 是没有新证据的状态，不写空账本记录。内容删除、评价撤销或关联纠正不覆盖旧记录，而是追加反向证据。

一条根内容必须确认 1 至 8 个寰点。回复不单独要求用户选点，而是继承根内容的已确认寰点。为避免通过大量短回复刷参与值，系统按用户—根内容—寰点实施可配置的每日有效回复上限；超过上限的回复仍可展示，但产生 `0` 新证据。

### 5.4 用户—寰点证据

- 发布或回复包含已确认寰点的内容：参与 `+1`。
- “正确”“有帮助”“实践有效”：认可 `+1`。
- “事实错误”“技术错误”“无法验证”：认可 `-1`。
- 普通观点分歧：`0`。
- “与寰点无关”：作者认可 `-1`，并可对域—寰点主题产生 `-1`。
- 用户不能评价自己的内容。
- 同一用户对同一内容版本的同一寰点只保留一条有效评价。

评价贡献使用评价发生时评价者在相同寰点上的认可等级系数快照，系数初始限制在 0.5 至 2.0 之间。尚未形成认可等级的评价者使用 1.0，避免冷启动用户没有评价能力；快照机制避免后续递归波动和无限放大。

### 5.5 域—寰点证据

- 种子寰点产生初始正向证据。
- 域内内容的已确认寰点产生主题 `+1`。
- 回复继承根内容的已确认寰点，并为回复者产生用户参与证据；同一回复—寰点只生成一次证据。
- 合法、非重复的结构化评价为被评价寰点产生域内互动证据；“与寰点无关”不增加正向主题互动，并额外产生主题 `-1`。
- “技术错误”不否定内容属于该主题。
- 只有“与寰点无关”才产生主题 `-1`。

域—寰点权重表示域是否持续讨论该主题，不表示域中的观点全部正确。

### 5.6 寰—寰点证据

- 用户主动绑定寰点产生全局热度 `+1`。
- 公开内容确认关联寰点产生全局热度 `+1`。
- 根内容、回复和合法结构化评价均属于有效参与；每个来源事件—寰点在寰中只计一次。
- 域内内容已属于寰，不因所属域重复计数。
- 域的种子寰点不直接增加全局热度。
- 系统预设或权威确认不直接增加全局热度。
- 首版不以浏览量直接增加权重。

### 5.7 证据账本

`weight_evidence` 至少包含：

- 稳定 ID。
- 目标范围：`USER`、`DOMAIN` 或 `HUAN`。
- 目标用户或目标域。
- 寰点 ID。
- 维度：参与、认可、主题或热度。
- 原始极性：`-1` 或 `+1`。
- 证据类型。
- 来源业务记录和 Outbox 事件 ID。
- 操作者。
- 发生时间。
- 计算策略版本。
- 评价者系数快照。
- 是否已被后续反向证据抵消。

证据账本不可变、可追溯、可幂等回放。

### 5.8 时间衰减

原始证据永久保存；当前贡献按关系和证据类型衰减：

```text
decay(age) = 2 ^ (-age / half_life)

current_contribution
= polarity
 × event_factor
 × actor_factor_snapshot
 × decay(age)
```

初始半衰期：

| 维度 | 半衰期 |
|---|---:|
| 用户参与 | 180 天 |
| 用户认可 | 720 天 |
| 域—寰点主题 | 120 天 |
| 寰—寰点热度 | 60 天 |

历史累计值不衰减。

### 5.9 用户综合契合公式

初始策略使用递减收益，避免高频发帖压过认可：

```text
participation_signal = ln(1 + max(participation_current, 0))

recognition_signal =
  sign(recognition_current) × ln(1 + abs(recognition_current))

user_composite =
  0.4 × participation_signal
  + 0.6 × recognition_signal
```

公式、系数和衰减均采用版本化配置。改变计算策略会创建新版本并重建投影。

### 5.10 权重投影

使用三张明确投影表：

- `user_point_weights`：当前参与、当前认可、当前综合、历史累计、策略版本和计算时间。
- `domain_point_weights`：当前主题、历史累计、种子标记、策略版本和计算时间。
- `huan_point_weights`：当前热度、历史累计、绑定用户数、关联内容数、策略版本和计算时间。

不使用缺少外键约束的多态权重大表。

## 6. 权重等级与颜色配置

### 6.1 配置原则

原始权重是数值事实；等级和颜色是可编辑展示映射。

三种关系：

- 共享同一套颜色体系。
- 独立配置等级名称、说明和数值区间。
- 独立配置衰减和证据系数。

修改等级名称、阈值或颜色不重算数值；修改公式、衰减或证据系数会创建策略版本并重建投影。

### 6.2 初始“寰宇星谱”

| 顺序 | 初始名称 | 初始颜色 |
|---:|---|---|
| 1 | 暗蚀 | `#9F1239` |
| 2 | 离轨 | `#C2410C` |
| 3 | 无光 | `#64748B` |
| 4 | 微光 | `#0891B2` |
| 5 | 星点 | `#2563EB` |
| 6 | 星轨 | `#4F46E5` |
| 7 | 星环 | `#7C3AED` |
| 8 | 星云 | `#C026D3` |
| 9 | 星系 | `#F59E0B` |
| 10 | 恒星 | `#FDE047` |

三套场景初始复用这些名称和色序，管理员可分别修改名称和区间。

### 6.3 配置校验

- 启用区间不能重叠。
- 启用区间不能留下无法匹配的空隙。
- 下限必须小于上限。
- 必须覆盖该权重场景的全部允许数值。
- 删除已使用等级前必须先停用或调整区间。
- 所有修改保留操作人、时间和变更记录。

## 7. 内容与寰点提取

### 7.1 内容模型

- 根内容标题；回复不需要标题。
- Markdown 正文。
- 内容类型。
- 作者。
- 可空的域 ID；空表示发布到寰。
- 可空的父内容 ID；为空表示根内容，非空表示回复。
- 当前版本。
- 已确认内容寰点。
- 发布、编辑、删除和处理状态。

Markdown 支持代码块、语法高亮、链接和图片。服务端必须按白名单清洗，不允许任意 HTML、脚本、事件属性、危险 URL 或 SVG 上传。

回复必须与根内容处于相同的寰或域语境，并继承根内容的已确认寰点。首版不为回复单独运行寰点确认流程；回复仍保存版本并可以被结构化评价。

### 7.2 提取流程

```text
标题 + Markdown 正文
  → 规范名称与别名精确匹配
  → pg_trgm 模糊匹配
  → 内容向量与寰点向量相似召回
  → 合并去重并标注来源和置信度
  → 发布者确认、移除、补充或创建寰点
  → 只提交已确认 ContentPoint
```

首版通过 Provider 接口调用本地 `bge-m3` 多语言嵌入模型，使用其 1024 维稠密向量，并在记录中保存模型名称和模型版本。pgvector 只负责存储和召回。向量服务不可用时，精确、别名、模糊和手工选择继续工作，向量任务进入重试，不阻止纯文字内容发布。

### 7.3 内容版本

- 修改标题、正文或寰点关联时创建 `content_revisions`。
- 实质修改使旧版本评价过期，并追加对应反向证据。
- 新版本可被重新评价。
- 非实质格式修改可以明确标记，不使评价失效。
- 删除内容会隐藏公开正文并追加反向证据，而不是覆盖历史账本。

## 8. 系统架构

### 8.1 总体选择

采用模块化单体、权重证据账本和异步投影：

```text
Next.js 桌面端
  → REST JSON
Gin API 进程
  → PostgreSQL 事务：业务数据 + Outbox
Go Worker 进程
  → 证据账本 + 权重投影 + 向量任务 + 搜索维护
```

API 和 Worker 来自同一个 Go 工程，作为两个进程运行。

HTTP API 使用 `/api/v1` 前缀，并以 OpenAPI 文档作为前后端接口契约。TypeScript 客户端由契约生成基础类型和请求封装；业务页面不直接拼接后端字段名或错误码。

### 8.2 后端模块

| 模块 | 职责 |
|---|---|
| `Account` | 注册、登录、会话、公开资料和最小系统通知 |
| `Point` | 寰点、产生方式、权威属性、别名、归一、向量 |
| `Domain` | 域创建、成员关联、种子寰点 |
| `Content` | Markdown、版本、回复、归属和内容寰点 |
| `Evaluation` | 结构化评价、理由和评价资格 |
| `Weight` | 证据账本、投影、衰减和重算 |
| `Discovery` | 全文、模糊、向量和混合排序 |
| `SystemConfig` | 等级、色谱、阈值、衰减和策略版本 |

模块只能修改自己拥有的表；跨模块通过公开接口、只读查询或 Outbox 协作。基础设施层只容纳日志、数据库、请求追踪、对象存储和向量 Provider 等无业务含义的适配器。

### 8.3 PostgreSQL 与 Redis

PostgreSQL + pgvector 是唯一事实数据源，保存业务数据、证据账本、Outbox、投影、配置、全文字段和向量。

Redis 只用于缓存、限流、任务唤醒和短期状态。Redis 清空后，核心事实不得丢失；Worker 必须能从 PostgreSQL 恢复。

### 8.4 事务和最终一致性

业务数据和 Outbox 位于同一 PostgreSQL 事务。内容和评价提交成功后立即可读取；权重和向量异步更新。界面显示最后计算时间和“权重计算中”状态。

每个事件具有稳定 ID；证据以事件 ID、目标关系和寰点建立幂等约束。失败重试、错误和下一次执行时间保存在 PostgreSQL。超过上限的事件进入管理员可见失败队列。

## 10. 桌面端信息架构

### 10.1 全局布局

桌面端采用三栏布局：左侧主导航、中央内容区域、右侧上下文信息。顶部始终保留全局搜索、发布内容和当前用户入口。

左侧导航：寰、发现寰点、我的域、我的名片、我的内容和最小系统通知。通知只包含权重处理完成、评价结果和平台操作结果，不承担私信或社交聊天。

### 10.2 页面路由

| 页面 | 路由 |
|---|---|
| 寰首页 | `/` |
| 全局搜索 | `/search` |
| 寰点详情 | `/points/[slug]` |
| 域详情 | `/domains/[slug]` |
| 内容详情 | `/contents/[id]` |
| 发布内容 | `/publish` |
| 用户名片 | `/users/[handle]` |
| 编辑名片 | `/settings/card` |
| 我的域 | `/me/domains` |
| 我的内容 | `/me/contents` |
| 寰点管理 | `/admin/points` |
| 权重配置 | `/admin/weight-schemes` |

公开页面由 Next.js 服务端渲染；发布、评价、设置和管理页面要求登录。

### 10.3 寰首页

- 聚合全部公开内容。
- 明确标注“发布于寰”或“来自某域”。
- 默认按用户寰点相似度、内容时效和质量混合排序。
- 可切换最新发布。
- 展示可解释匹配原因，不采用无法解释的纯黑盒信息流。

### 10.4 寰点详情

展示规范名称、描述、别名、产生方式、权威属性和依据、全局热度、相关内容、域、用户和寰点。内容、域和用户使用独立标签页。

产生方式和权威属性分开显示，例如“系统预设 / 公共标准”。用户名片上的等级不能显示成用户能力认证。

### 10.5 域详情

展示名称、描述、创建关联、成员数、动态寰点向量、公开内容和加入入口。加入后才能发布、回复和评价。

### 10.6 用户名片

默认展示公开资料、绑定寰点、当前综合等级、颜色和最近公开参与。展开等级后展示参与值、认可值、综合值、证据摘要、最后计算时间和策略版本。

### 10.7 发布流程

1. 选择寰或一个已加入的域。
2. 选择内容类型。
3. 编写标题和 Markdown 正文。
4. 请求候选寰点。
5. 查看匹配来源和置信度。
6. 确认、移除、补充或创建寰点。
7. 发布内容。
8. 内容立即可读，权重和向量异步更新。

### 10.8 结构化评价

评价必须选择具体内容寰点、方向和结构化理由，可补充简短说明。用户不能评价自己；修改评价会追加撤销和新证据，不覆盖历史。

## 11. 账号、安全和隐私

### 11.1 账号

- 邀请码、邮箱、唯一用户名和密码注册。
- Argon2id 密码哈希。
- HttpOnly、Secure、SameSite=Lax 会话 Cookie。
- 修改密码、退出全部设备或停用账号会撤销旧会话。
- 密码重置使用短期一次性令牌。
- 角色只有 `MEMBER` 和 `PLATFORM_ADMIN`。

### 11.2 内容安全

- 服务端白名单清洗 Markdown。
- 禁止任意 HTML、脚本、事件属性和危险 URL。
- 代码块只高亮，不执行。
- 图片通过 S3 兼容对象存储，校验 MIME、大小和扩展名。
- 对象键随机生成。
- 首版不允许 SVG、可执行文件或任意附件。

### 11.3 反滥用最低边界

- 邀请制账号仍执行发布、回复、创建寰点和评价限流。
- 新账号的每日寰点创建上限更低。
- 同一评价者对同一作者的高频评价受限。
- 负向评价必须有结构化理由。
- 评价者系数有上限。
- 被停用账号的新证据不进入当前投影。
- 管理员不能直接修改权重。

### 11.4 删除

删除账号会撤销会话、匿名化公开资料并停止展示个人权重。内容按用户选择删除或转为匿名作者。最小审计元数据和反向证据保留；不再需要的私人资料删除。

## 12. 错误与降级

### 12.1 API 错误

统一返回业务错误码、用户消息、字段错误、是否可重试和 `trace_id`：

```json
{
  "code": "CONTENT_POINT_INVALID",
  "message": "存在已经失效或合并的寰点",
  "field_errors": {
    "point_ids": ["请重新选择规范寰点"]
  },
  "retryable": false,
  "trace_id": "01J..."
}
```

| HTTP 状态 | 场景 |
|---:|---|
| `400` | 请求格式错误 |
| `401` | 未登录或会话失效 |
| `403` | 没有管理员权限或未加入目标域 |
| `404` | 资源不存在或已停用 |
| `409` | 重复评价、名称冲突或内容版本冲突 |
| `422` | 字段合法但不满足业务规则 |
| `429` | 发布、评价或创建寰点超过限制 |
| `503` | 向量、对象存储等依赖暂时不可用 |

客户端必须保留失败的发布草稿，写操作携带幂等键，不能在网络错误时盲目重复提交。

### 12.2 向量服务不可用

精确、别名、模糊和手工选择继续工作；内容允许发布；向量任务保留并重试。

### 12.3 Redis 不可用

核心业务回源 PostgreSQL；Worker 轮询 Outbox；限流降级为保守的进程级限制；核心事实不丢失。

### 12.4 对象存储不可用

文字草稿保留；新图片上传失败不创建半完成记录；用户可移除图片后发布纯文字内容。

### 12.5 投影延迟

业务事实仍然提交成功；界面显示最后计算时间和待更新状态；Worker 恢复后继续处理且不重复计数。

## 13. 可观测性

- `/health/live`。
- `/health/ready`。
- 结构化 JSON 日志和请求 `trace_id`。
- API 延迟、错误率和状态码指标。
- Outbox 堆积和 Worker 失败指标。
- 权重投影延迟和向量任务成功率。
- PostgreSQL 定期备份和恢复验证。
- 对象存储备份。
- 日志不得记录密码、令牌、完整 Cookie 或私人字段。

## 14. 测试策略

### 14.1 Go 单元与性质测试

覆盖寰点归一、产生方式、权威属性、内容寰点确认、评价规则、证据生成、时间衰减、综合公式、等级匹配、内容撤销和寰点合并。

必须验证：

- 同一证据集和策略得到确定结果。
- 同一事件重放不重复计数。
- 时间增加时当前贡献不反向增大。
- 修改等级颜色不改变数值。
- 全量重算与增量投影一致。
- 域内容不会在寰重复计数。
- 合并前后证据总量守恒。
- 反向证据准确抵消。
- 等级区间无重叠和空隙。

### 14.2 数据库集成测试

使用真实 PostgreSQL 和 pgvector 测试迁移、事务与 Outbox 原子性、约束、并发消费、重建、合并和混合召回。

### 14.3 前端测试

使用 Vitest 和 React Testing Library 测试表单、状态、Markdown 安全、等级映射、草稿保留、投影延迟和权威标识。

### 14.4 端到端测试

使用 Playwright 覆盖：受邀注册、绑定寰点、创建和加入域、发布内容、确认寰点、全局搜索、结构化评价、三类投影更新、名片展示和管理员修改颜色。

## 15. 验收标准

首版必须满足：

1. 邀请用户可注册、登录和退出。
2. 系统可幂等初始化预设寰点。
3. 用户可创建、搜索、绑定和移除寰点。
4. 寰点同时具有产生方式和权威属性。
5. 管理员可录入、导入、归一和设置权威属性。
6. 用户可创建公开域并选择多个种子寰点。
7. 用户可加入域。
8. 用户可直接发布到寰或一个已加入的域。
9. Markdown、代码块、链接和图片安全展示。
10. 系统可生成精确、别名、模糊和向量候选。
11. 发布者可确认候选或创建新寰点。
12. 域内容在寰中可搜索并标注来源域。
13. 用户可针对具体内容寰点结构化评价。
14. 发布和评价形成可审计三值证据。
15. Worker 幂等计算三类投影。
16. 用户—寰点区分参与值和认可值。
17. 当前值按配置衰减，历史累计值不衰减。
18. 名片、域和寰点页面可解释当前等级。
19. 三套等级共享色谱，名称和阈值独立配置。
20. 修改展示配置不重算；修改公式和衰减可重建。
21. 内容修改、删除和评价撤销生成正确反向证据。
22. 同义寰点合并后关系和权重不丢失。
23. Redis 或向量服务短暂不可用时核心事实不丢失。
24. 核心闭环具有自动化端到端测试。
25. 关键功能有必要注释，模块边界清晰。

内测基线：

- 至少 500 个受邀账号。
- 至少 50 个并发活跃用户。
- 常规读取接口 `p95 < 500ms`。
- 不包含向量生成的写接口 `p95 < 800ms`。
- 混合搜索 `p95 < 1.5s`。
- 正常情况下权重投影在业务事务提交后 10 秒内更新。
- Worker 重启后继续处理且不重复计数。

性能基线以单个 API/Worker 部署各 4 vCPU、8 GB 内存，PostgreSQL 4 vCPU、8 GB 内存，Redis 1 GB 内存的内测参考环境为准；向量模型推理资源单独计算。性能测试使用固定数据集和相同环境重复执行，避免把本地偶然结果当作验收结论。

## 16. 明确排除项

首版不实现：

- 移动端布局或原生移动应用。
- 实时聊天、私信、语音或视频。
- 私密域。
- 一条内容同时归属于多个域。
- 域管理员、域治理、选举或投票。
- 系统自动创建正式域。
- 候选域自动孵化界面。
- 复杂推荐服务。
- 大模型直接生成寰点。
- 公开互联网级内容审核平台。
- 大规模反作弊与关系图风控。
- 支付、订阅或虚拟货币。
- 关注用户、好友关系或社交私信。
- 第三方登录。
- 微服务拆分。
- Elasticsearch 或图数据库。
- 用户能力官方认证体系。

寰点可以具有 `PUBLIC_STANDARD` 或 `EXTERNAL_AUTHORITY`，但这不等于平台认证某个用户拥有相应能力。

## 17. 关键设计决策汇总

- 寰是唯一官方总域；域是用户定义的小寰。
- 内容属于寰或一个域，域内容仍在寰中可见。
- 所有寰点诞生即进入寰。
- 寰点的产生方式和权威属性分开建模。
- 同义归一由官方确认，合并不丢历史证据。
- 用户内部双权重，对外一个综合等级。
- 原始证据永久保存，当前值按策略衰减。
- 展示等级和颜色可编辑，不写死在代码中。
- 初始色谱采用“寰宇星谱”。
- 采用模块化单体、PostgreSQL Outbox、API 与 Worker 双进程。
- PostgreSQL 是事实数据源，Redis 可清空恢复。
- 首版专注权重闭环，不实现域治理、实时聊天或移动端。

## 18. 实施切片原则

后续实施计划必须按可运行的纵向切片推进，而不是同时铺开所有目录：

1. 工程基础、数据库迁移、账号和邀请登录。
2. 寰点目录、产生方式、权威属性、系统预设和官方归一。
3. 寰、公开域、成员关系、Markdown 内容和内容版本。
4. 内容寰点提取、pgvector 与混合搜索。
5. 结构化评价、Outbox、证据账本和三类权重投影。
6. 名片、域向量、全局热度和可解释展示。
7. 权重等级配置、策略版本和投影重建。
8. 降级、审计、性能、备份和完整端到端验收。

每个切片必须具有可执行迁移、后端行为、桌面端界面和自动化验证；不得以只创建空模块或只完成表结构作为功能完成。
